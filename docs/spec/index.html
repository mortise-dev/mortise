Mortise: design specification

Phase 0, design and information architecture. 22 November 2026. For the people who build the app.

Mortise is a desktop companion for developers who build Laravel apps with nwidart/laravel-modules. It opens the folder of an app, lists its modules, shows what is in each one, which module uses which and where a boundary is broken, what the running app reports, and later creates modules and files and runs the package's commands with their output on screen. It is a native app written in Rust with egui, open source, for macOS, Linux and Windows, in a light and a dark theme.

This document closes phase 0, design and information architecture. It is what the people who build the app work from. No app code exists yet. All data in the drawings is invented: an app named shop-api with seven modules.

1.1 Decisions already made by the owner

These are fixed. The spec does not reopen them.

SubjectDecision
NameMortise.
StructureA three column, keyboard first workbench: a narrow app rail, a module index that is always visible, a workspace with five tabs (Summary, Boundary, Generate, Actions, Metrics), a command palette on Cmd or Ctrl K, a runner drawer at the bottom for command output.
IdentityTimber joinery. No accent hue: colour only for state. The selected row is keyed through the joint line into the workspace. Three letter module code stamps. Asap and Inconsolata.
Background hueSlate, a blue grey, replaces the brown neutrals. State colours and the oak and walnut app icon are unchanged.
Title barThe slim title bar with the mark and the entry to the command palette stays.
Themes and platformsLight and dark, both first class. macOS, Linux and Windows.
TechnologyRust with egui: immediate mode, drawn on the GPU, everything custom. Flat fills, strokes, rounded rectangles, simple shadows, vector icons and bundled fonts. No backdrop blur, no native controls.
DistributionOpen source desktop app. A paid cloud service comes much later and is not part of this spec.
Phases1 is read only: apps, modules, statistics, boundary graph, findings. It needs no PHP and no package change. 2 writes: new module, generators, actions. It needs PHP and package additions. 3 is live metrics.
Outlines on the frame colour (answer to Q1)Accepted. Controls on frame are outlined in ink-2, because line-2 is under 3 to 1 there in the light theme. It is a token rule.
Boundary rules file (Q2)Rules are kept in mortise.json in the app folder, with that name.
A module's public surface (Q3)The package will define it. Mortise offers a scan, on demand, that proposes the public surface of one module, including what it exposes over HTTP and on the command line. Where the accepted surface is stored is the package's decision and is not made yet.
Destructive commands (Q6)Mortise offers all four: module:migrate-reset, module:migrate-refresh, module:migrate-fresh and module:delete, with the strongest confirmation in the app.
Tests (Q7)Per module. The package will provide a command that runs the tests of one module.
Actuator credentials (Q12)Left to this spec: none, bearer token, HTTP basic, custom header. Secrets go to the credential store of the operating system, never to mortise.json or a config file, and are not shown again.
A circular link (Q4)Is counted once, on the module with fewer files in the circle; the other module shows the link in its Boundary tab. S5.2
A waiting migration (Q5)Is work to do, not a finding. It is listed under "To do" and changes no state mark. S6.4
Shortcuts (Q8)Fixed in the first release, not changeable in Settings. / and ` have second bindings, Ctrl F and Ctrl J, for layouts where they are hard to type.
Runner toggle on macOS (Q9)Ctrl ` on every platform, because Cmd ` belongs to macOS for cycling windows.
Tabs of a later phase (Q10)The five tabs are always shown and a tab that is not built explains itself. Buttons, footer actions and palette entries of a later phase are hidden. S7.4
Runtime status on the rail (Q11)A runtime Down raises no pip on a rail tile, for any environment. The pip is for findings of the kind problem only. S2.1
Module groups (Q13)Kept by Mortise per app, not in module.json or any file of the app. S3.1
Features outside this spec (Q14)Recipes, the stub editor, the explorer, git owners and the upgrade helper are not part of phases 1 to 3 as specified here. "Save as recipe" stays out of the Generate form.
Reading .env (Q15)Mortise reads two lines, APP_URL and APP_ENV, and no others. S1.3
Metrics without limits (Q16)The Metrics tab shows numbers without limits or colour. The desktop app has no user-set limits; alerts belong to the later cloud plan. S7.3
ActuatorApps also have nwidart/laravel-actuator 1.0.0. It is a data source from phase 1 on, optional. Release 13.4.0 of nwidart/laravel-modules has module aware health indicators and a modules endpoint with no routes or tasks. Actuator 1.3.1 has custom endpoints and a prometheus endpoint, whose module label no code fills in. Per module routes, tasks and metrics need package work first.

1.3 How to read this

  • Pages follow the twelve sections of the brief. The list is below and at the top of every page.
  • Every screen and state has an id such as S4.2, shown before its title. Flows, tables and notes refer to screens by id, and each id is a link.
  • Drawings are real HTML and CSS using the Mortise stylesheet with the Slate values. They are drawings of an egui app, not a web app: nothing in them is interactive.
  • Themes. Each page with drawings has a switch at the top for its switchable drawings; the state is kept in memory only. Where the two themes matter for a decision, both are drawn side by side and need no JavaScript. Adding #dark to a page address opens it in dark.
  • Under each drawing: the phase it belongs to, where its data comes from, and what it assumes that the packages do not offer today, with a code such as P2 that links to the list in section 12.
  • Shortcuts in drawings are written for Windows and Linux. On macOS Ctrl is Cmd, with the one exception named in section 7.
  • Sizes are logical pixels at 100% text size.

1.6 Not in this spec

  • The cloud service, teams, alerts and hosted history.
  • Recipes, the stub editor, the explorer of routes and events, git owners and the upgrade helper from the first feature list. "Save as recipe" was removed from the Generate form for that reason.
  • The command line twin for CI. It appears once, as a rule that is not available yet.
  • The website, the installer and the update mechanism.
  • Any code.
