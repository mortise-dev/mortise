Flows and keyboard

Mortise design specification, sections 6 and 7. The five flows for mouse and keyboard, the shortcut table, the focus order.

Sections 6 and 7 of the specification. The first five flows are the ones the workbench structure was chosen for; the sixth was added with the public surface scan. Each is given step by step, once for the mouse and once for the keyboard, with the screen each step lands on. Shortcuts in the steps are written for Windows and Linux; on macOS Ctrl is Cmd, except where the table in section 7 says otherwise.

6. Flows

F1Add an app

From an empty Mortise to the modules of booking-engine on screen. 3 actions.

With the mouse

  1. Click the dashed + tile on the rail, or "Add app folder" on the first run screen S1.1. The add panel opens S1.2.
  2. Click "Choose folder" and pick ~/code/booking-engine in the folder dialog, or drop the folder on the window. The panel shows what was found S1.3. If something is wrong it says so at the field S1.4.
  3. Click "Add booking-engine". Its tile appears on the rail and is selected; the index lists its modules and the workspace shows its Summary S4.2.

With the keyboard

  1. Press Ctrl O from anywhere. The folder dialog of the operating system opens at once.
  2. Choose the folder there and confirm. Focus lands on the "Add booking-engine" button S1.3; Tab reaches the PHP and runtime choices if they need changing.
  3. Press Enter or Ctrl Enter. Focus moves to the "All modules" row of the new app S4.2.
Also. Ctrl K, "add", Enter opens the same panel. A toast confirms: "Added booking-engine. 5 modules read."

F2Find the module with a problem and see what is wrong

From the home screen to the two findings of Checkout. 1 action.

With the mouse

  1. On the home screen S4.1 the index already shows the problem mark and "2" on Checkout, and the alert names it. Click the Checkout row. Its Summary opens with both problems in the alert at the top S4.3.
  2. Optional: click "Show all 3 findings" on the home screen for the list of the whole app S6.4, or the Boundary tab for the files S5.1.

With the keyboard

  1. Press J. With the index sorted problems first, Checkout is the first module under "All modules", and its Summary is on screen in the same frame S4.3.
  2. Optional: press F for the findings list S6.4, where Enter on a finding opens it where it lives; or press 2 for Boundary S5.1.
If the index is sorted by name. Press S once, or read the pip on the rail and the Findings stat. With 60 modules the pinned group "Needs attention" does the same job S3.1.

F3Create a model with a migration and a policy

A new model PaymentIntent in Billing, with its migration and policy. 4 actions. Phase 2.

With the mouse

  1. Click Billing in the index, then the Generate tab. The picker opens with Model first S9.1.
  2. Click Model. Type PaymentIntent in "Model name" and the fillable attributes if wanted S9.2.
  3. Check Migration and Policy. Read the command and the three files on the right. If a file exists already the preview says so S9.3.
  4. Click "Create 3 files". The result replaces the preview and the runner drawer shows the output S9.5; on a failure it says which file and what to do S9.6.

With the keyboard

  1. Press Ctrl K, type model bil, press Enter. The form opens with Billing as the module and focus in "Model name" S9.2.
  2. Type PaymentIntent, Tab, type the fillable attributes.
  3. Tab to Migration, Space. Tab to Policy, Space. The command and the file list update as you go.
  4. Press Ctrl Enter S9.5. Enter then opens the model in the editor.
Without the palette. J or K to Billing, G, type mod, Enter.

F4Run migrations for one module and read the output

The waiting migration of Checkout runs and its output is on screen. 2 actions. Phase 2.

With the mouse

  1. Click Checkout in the index S4.3.
  2. Click "Migrate (1)" in the module header. The runner drawer opens under the workspace with the command and its output as it arrives; when it ends the status reads "Done in 186 ms" or "Exit code 1" with the next steps S11.1.

With the keyboard

  1. Press J to select Checkout.
  2. Press 4 for Actions; Migrate is selected because a migration waits S10.1. Press Ctrl Enter. Focus stays where it was; the drawer shows the output S11.1. Ctrl ` hides it.
With options. A dry run or seeding afterwards are the two checkboxes on the Actions tab. In production Mortise asks first S10.3.
From the palette. Ctrl K, migrate chk, Enter.

F5See why two modules depend on each other

From Checkout to the six files that make Checkout and Shipping use each other. 2 actions.

With the mouse

  1. Click Checkout in the index.
  2. Click the Boundary tab. Checkout is in the middle with Shipping on both sides, both links drawn as problems S5.1. Click either Shipping node: the files of both directions are listed below, with the line and the class each one reads S5.2.

With the keyboard

  1. Press J to select Checkout.
  2. Press 2. Focus is on the first problem link. Arrow keys move between the modules of the graph S5.1; on Shipping the list below shows the files S5.2. Tab moves into the list, J and K move through it, Enter opens a file at its line in the editor.
From the app. On "All modules", Boundary lists the links that break a rule; Enter on "Checkout and Shipping use each other" lands on the same view S5.3.

F6Propose and accept the public surface of a module

Added after the owner's answer on the public surface. From Billing to an accepted list of what Billing offers to other modules, to HTTP clients and to the command line. 4 actions. Accepting needs the package (P6).

With the mouse

  1. Click Billing in the index, then the Boundary tab, then "Public surface" in the control at the top S5.5.
  2. Click "Scan Billing". The view shows the scan as it reads S5.6, then the proposal S5.7.
  3. Read the list. Click a checkbox to leave an entry out or take one in; type in the field at the bottom to add one by hand.
  4. Click "Accept 21 entries". The view shows the accepted surface S5.8 and the findings are worked out again.

With the keyboard

  1. J or K to Billing, 2 for Boundary, P for Public surface S5.5.
  2. Ctrl Enter starts the scan S5.6. Esc stops it. When it ends, focus is on the first entry of the proposal S5.7.
  3. J and K move through the entries, Space includes one or leaves it out, A goes to the add field, Enter there adds the entry.
  4. Ctrl Enter accepts S5.8.
Later. The same Ctrl Enter in the accepted view scans again. If the code has changed, only the differences are listed, each to accept or to leave S5.9.
From the palette. Ctrl K, surface bil, Enter opens the view; it does not start the scan.

Rules behind the table.

  • Everything can be done without a pointer. Nothing is reachable only by hover or by dragging: the index width and the drawer height have keys, and the palette reaches every command.
  • Single letters never act while a text field has focus. Esc leaves the field first.
  • A shortcut is shown where its action is: in the button, in the tab, in the palette row, in the tooltip.
  • Keys that are awkward on some keyboard layouts have a second binding with a modifier: / and `.

K1Focus order of the main window

Tab moves through controls in this order; Shift Tab goes back. F6 jumps between the four regions. A list, a table, the tab row and a segmented control are each one stop: arrows move inside them.

  • At start, focus is on the selected row of the index, so J, K and the digit keys work at once.
  • Selecting a module with J or K leaves focus in the index. Enter or Right moves it to the first control of the tab; Esc brings it back.
  • Switching tab with a digit leaves focus where it was, except on Generate, where it goes to the first field of the form.
  • The palette and a dialog hold focus until they close, then return it to where it was. Tab does not leave them.
  • Window controls drawn by Mortise (Windows, Linux) are not in the Tab order; the platform's own keys work for them.
  • A command that ends does not move focus. The drawer opening never takes focus.
