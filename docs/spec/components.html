Components

Mortise design specification, section 4. Every component in every state, with sizes in pixels.

Section 4 of the specification. Every component is drawn in each state it has, in light and dark side by side. The components and their look come from the Mortise identity and are not redesigned here; this page adds the states the identity did not draw (hover, focus, pressed, disabled, error) and the components it did not have (segmented control, table, tooltip, toast, dialog, scrollbar, progress, runtime marks).

States, one rule each. Hover: the fill becomes well. Pressed: the fill becomes line. Keyboard focus: a 2 px ink ring, 1 px outside the control, on top of any other state. Selected: the joint, or on a list row the well fill with a line above and below, and the peg. Disabled: the outline drops to line and the label to ink-3; a disabled control keeps its place and says why in a tooltip. Error: the outline becomes bad and a sentence with the problem mark sits under the field. Hover and pressed exist for the pointer only; nothing is revealed on hover that the keyboard cannot reach.

How a code is made. Mortise proposes one from the name: the first three letters of a short name, or the first letter and the consonants that follow (Checkout: CHK, Notifications: NTF, Shipping: SHP). It must be unique within the app; ALL is reserved. The user can change a code in Settings. A code never changes by itself once given, so it can be learned. The exact proposal rule is for the builders; uniqueness and stability are the requirements.

An empty state says what is missing and gives the one action that fills it. Other titles and paragraphs: "Generate needs PHP" Mortise could not run PHP for shop-api: "herd: command not found". Choose how PHP runs for this app in Settings.   "Generate needs a newer nwidart/laravel-modules" shop-api has 13.3.0. The preview needs the dry run that a later version adds. It needs PHP and a newer nwidart/laravel-modules, and arrives in a later release of Mortise.
