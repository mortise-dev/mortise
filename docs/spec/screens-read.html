Mortise design specification, section 5, part 2. Summary, Boundary, Findings, runtime status, Metrics.

Theme for the switchable drawings on this page. Kept in memory only. Without JavaScript they stay light; the paired drawings always show both.

Section 5, part 2 of 4: everything Mortise reads and shows. Summary, Boundary, Findings, runtime status and Metrics. None of these screens writes to the app, except the rules file in S5.3.

Two names that are kept apart. Findings are what Mortise works out from the files: problems, warnings, good, drawn as solid marks. Runtime is what the running app reports through the actuator: Up, Down, Out of service, Unknown, drawn as stroke marks. The word "health" is not used in the interface for either.

5.5 Boundary, second view: the public surface of a module

The owner decided that the package will define a module's public surface, and that Mortise offers a scan, on demand, that proposes one. The surface is everything of a module that something outside it may use: PHP classes for other modules, routes for HTTP clients, console commands for the command line and the scheduler. It lives in the Boundary tab of one module as a second view beside the links; no surface was added. The drawings use Billing, because its scan settles the open finding: Checkout reads Billing\Models\Invoice.

Generate is not in this version

Generate creates modules and files through the package's own commands, with a preview before anything is written. It needs PHP and a newer nwidart/laravel-modules, and arrives in a later release of Mortise.

Phase. A phase 1 build, Generate tab. Actions and Metrics use the same block.
Why shown. Keys 1 to 5 keep their meaning across releases, and the same block is needed for good in two other cases: Mortise could not run PHP for shop-api: "herd: command not found". Choose how PHP runs for this app in Settings.   shop-api has 13.3.0. The preview needs the dry run that a later version adds. Run composer update nwidart/laravel-modules in the app.
Why actions are hidden. A header with three disabled buttons on every module is noise. In a phase 1 build the module header has only "Open in editor", the index footer has no "New module", and the palette lists no generators or actions.
Disabled, not hidden. In a build that has the phase, a control the app cannot run (PHP not found, package too old) is drawn disabled with the reason in a tooltip: "Needs PHP. Choose how PHP runs in Settings."
Assumes. Nothing the packages lack today.
