The Generate tab is tab 3 of the workspace. It runs the generators of `nwidart/laravel-modules`.

| Keys | Does |
|---|---|
| <kbd>3</kbd> | Opens the tab. Focus stays where it was. |
| <kbd>G</kbd> | Opens the tab with the generator filter focused. |
| <kbd>Ctrl</kbd> <kbd>N</kbd> (<kbd>Cmd</kbd> <kbd>N</kbd> on macOS) | Selects **All modules** and opens the new module form. |
| <kbd>Ctrl</kbd> <kbd>Enter</kbd> (<kbd>Cmd</kbd> <kbd>Enter</kbd> on macOS) | Runs the line the form shows. |
| <kbd>Ctrl</kbd> <kbd>Shift</kbd> <kbd>C</kbd> (<kbd>Cmd</kbd> <kbd>Shift</kbd> <kbd>C</kbd> on macOS) | Copies the command. |

## The picker

<Screen
  id="s9.1-picker"
  alt="The generator picker of the module Billing: a filter field, then the generators in groups such as Data, HTTP and Events and queues."
/>

The picker lists the generators in groups, in this order: **In the app**, **Data**, **HTTP**,
**Events and queues**, **Views**, **Classes**, **Console and setup**, **Tests**. A generator that
Mortise does not place, such as one the app adds itself, goes to a last group, **Other**, sorted by name.

- With a module selected, the line under the filter reads, for example,
  "41 generators for Billing, and New module. Enter opens the form."
- With **All modules** selected, the picker lists New module only, with the line
  "Select a module in the index to generate files in it."
- Typing in **Find a generator** filters by label and by artisan name.
- <kbd>Up</kbd>, <kbd>Down</kbd>, <kbd>Left</kbd> and <kbd>Right</kbd> move. <kbd>Enter</kbd> opens
  the form. <kbd>Esc</kbd> clears the filter.

### Which list the picker shows

Mortise reads the version of `nwidart/laravel-modules` from `composer.lock`.

| App's package | List |
|---|---|
| Before 13.4.0, or a dev, branch or pre-release version | The 42 generators of 13.3.0, shipped with Mortise |
| 13.4.0 or later | The 43 generators of 13.4.0, shipped with Mortise, until you read the generators of the app |
| 13.4.0 or later, after a read | The generators read from the app |

The 13.4.0 list adds `module:make-health-indicator` to the 13.3.0 list. The options of the other
generators are the same in both lists, apart from `--dry-run` and `--json`.

When the shipped list is of another minor version than the app's, the picker is marked, for example
"for nwidart/laravel-modules 13.3".

### Read the generators of the app

On 13.4.0 and later the picker offers **Read the generators of `<app>`**, with its line on screen:
`module:generators --no-interaction --ansi --json` behind the runner prefix. Mortise reads the list
only when you press the button.

- The list read replaces the shipped one for that app. A generator of the app's own shows under **Other**, with its form.
- After a read the picker says, for example, "Read from shop-api at 14:05." beside **Read again**.
- The list is kept in Mortise's data folder, under `catalogs/`, for that app and that package
  version. A new package version makes it stale. See [Files and folders](/mortise/reference/files-and-folders/).
- A read that gives no list says: "Mortise could not read the generators of `<app>`: "`<reason>`".
  The list is the one shipped for 13.4."

## The generators

Each form is built from the package's description of the generator. The module argument is filled
from the selection. An option with a value is a text field. A flag is a checkbox under **Options**.
Both are labelled with the package's own description, without its full stop, with the option beside it.

`--force` is on no form except the new module form. Replace is the way to write over a file.
`--dry-run` and `--json` are on no form: Mortise adds them itself.

The table lists the 43 generators of 13.4.0, by group. "Class name" and "no spaces" are the
[name checks](#name-checks).

## The model form

The form of `module:make-model` has its own fields.

<Screen
  id="s9.2-model-files"
  alt="The model form of Billing with the name PaymentIntent, Migration and Policy checked, the command line and the list of the three files it creates."
/>

| Field | Word |
|---|---|
| **Model name** | The model argument, checked as a class name |
| **Fillable attributes** (`--fillable, comma separated`) | `--fillable=<value>` |
| **Also create**: Controller, Factory, Migration, Request, Resource, Policy, Seeder | `--controller`, `--factory`, `--migration`, `--request`, `--resource`, `--policy`, `--seed` |
| **All of these** | `--all`, in place of the seven flags. Checking it checks the seven boxes |
| **Use Eloquent attributes such as #[Fillable]** | `--attributes` |

Checking all seven boxes also gives `--all`.

## The new module form

**New module** in the index footer, in the picker, in the palette, and <kbd>Ctrl</kbd> <kbd>N</kbd>
open this form. The form selects **All modules**. Its title is "New module in `<app>`".

| Field | Word |
|---|---|
| **Module names** (one or more, separated by spaces) | One word per name, each checked as a module name |
| **Kind** (`--web is the default`): Web, API, Plain | Web adds no flag. API adds `--api`. Plain adds `--plain` |
| **Inertia controller and pages, no Blade views** | `--inertia` |
| **Turn the module on after creation** (unchecked adds --disabled) | Unchecked adds `--disabled` |
| **Replace the module if it exists** | `--force`. The run then asks first |
| **Author** (optional, written to composer.json): Name, Email, Vendor | `--author-name=`, `--author-email=`, `--author-vendor=` |

The button reads **Create module**. Before 13.4 the form also says
"Then the command runs composer dump-autoload in the app."

## Name checks

While a name fails, the error shows under its field and the run button is off. An empty name turns
the button off without an error.

| Rule | Generators | Passes |
|---|---|---|
| Class name | Every generator not listed below | One or more parts split on `/` or `\`. Each part starts with an ASCII letter, then ASCII letters, digits or `_`. `create_posts_table` passes |
| No spaces | View, Component view, Config, Inertia page, Inertia component | No white space, and no `-` at the start |
| Module name | New module | An ASCII letter, then ASCII letters, digits, `-` or `_` |

Examples of the errors:

- "A model name starts with a letter and has no spaces. Write PaymentIntent, not "payment intent"."
- "The module name [2fa] is not valid. Use letters, digits, "-", "_" or spaces, starting with a letter."

## The command line

The line under **Command** is the line the run button starts, rebuilt on every change. It holds the
runner prefix and `--no-interaction --ansi`, quoted for the shell of the platform.

- Each value is one word, such as `--fillable=order_id,amount,currency,status`. No shell reads it.
- When an argument starts with `-`, the arguments go last, after `--`.
- The run button and <kbd>Ctrl</kbd> <kbd>Enter</kbd> run only a line that was whole on screen.
  While it was not, the button is off with the tooltip "Scroll up to see the whole command first."
- Without a runner, while a name fails, or while a command runs in the app, the button is off.

On 13.4.0 and later, a run of a generator the package ships also carries `--json`. Mortise reads
the result from that answer.

## List files

How the form shows the files depends on the package version.

| App's package | Under the command | Button |
|---|---|---|
| Before 13.4.0, or a generator of the app's own | "The files are listed after the run." | **Create files**, or **Create module** |
| 13.4.0 or later | **List files**, with the line of the dry run on screen | **Create `<n>` files** after a list |

**List files** runs the generator with `--dry-run --json`. The dry run creates and changes no file.
It runs only when you press the button, never on a keystroke.

- After the dry run, the form lists the files under **Files this creates**, by folder. The head
  counts them: "3 files, none exist yet" or "3 files, 1 exists already".
- The button counts them: **Create 3 files**.
- Any change of the command drops the list. **List files again** beside the head asks for a fresh answer.
- A dry run that gives no list says: "The dry run gave no file list: "`<reason>`"."

### A file that exists

A generator does not write over a file. When the dry run reports that a file exists:

- On the model form, the flag of that file is unchecked and marked **exists**, and it leaves the line.
  The button reads, for example, **Create the other 2 files**. The factory is the exception: the
  model uses its factory, so `--factory` stays and the run leaves the file as it is.
- When the generator's own file exists, the form says to choose another name, or to replace the file.

## The result of a run

When a run ends, the form keeps its values and shows the files:

| Row | Means |
|---|---|
| (no mark) | Created |
| **replaced** | Written again with `--force` |
| **exists, left as it is** | The file was there and the run left it |
| **not written** | The output names the file as not written, for another reason |

Each file that exists has **Open**. The head reads, for example, "Created in Billing" or "Created 2 of 3 files".
**Generate another** goes back to the form with the name cleared and the rest kept.

- A run that created every file shows the toast "Created 3 files in Billing."
- A run that left a file shows an alert, such as "Created 2 of 3 files in Billing. InvoicePolicy.php
  already exists and was left as it is.", with **Open the existing file**.
- The result never comes from the exit code.
- On 13.4.0 and later, the files come from the package's JSON answer. When that answer is missing or
  cannot be read, they come from the output lines, and the result says
  "Read from the output: the package's answer was "`<reason>`"."

## Replace

### Replace a file

When Mortise knows the generator that writes a left file, the result offers **Replace `<file>`**.

<Screen
  id="s9.6-replace"
  alt="The dialog Replace InvoicePolicy.php? with the line it runs and the buttons Cancel and Replace file."
/>

The dialog "Replace `<file>`?" says: "The file exists. The generator writes a new one over it, and
Mortise cannot bring the old one back." It shows the line it runs. Focus starts on **Cancel**.
Only **Replace file** runs the generator again with `--force`, for example
`module:make-policy InvoicePolicy Billing --force`.

### Replace a module

With **Replace the module if it exists** checked, the run asks first. The dialog
"Replace the module `<Module>`?" shows the line and says, for example:
"Modules/Loyalty exists with 23 files. module:make --force deletes the folder, then generates the
module again. Files you wrote in it are lost." Nothing runs until **Replace module**.
